Up until now the bot had been running locally on my machine. The next step was to host it in order that people can actually start chatting with it.

There are different ways I could have hosted the bot but I decided to go with Kubernetes. The reason being is that I have wanted to learn Kubernetes for some time now, but just didn’t have a suitable project to take the plunge.

This and a follow up post will detail how I went about setting up an end to end build and deployment pipeline for the theme park bot.

Part 1 details setting up the Kubernetes cluster and supporting infrastructure in Azure. All the code presented is available on my GitHub at: themeparks-infrastructure.

Tools

There are a number of different tools I used in setting up the deployment pipeline, each described below.

Azure

Azure is Microsoft’s cloud platform which I am using to host all the infrastructure for the bot.

I decided to use Azure because I already have a lot of pre-existing knowledge of building and deploying applications on Azure. This meant that I could then focus more on learning Kubernetes, rather than cloud platform’s specifics.

Azure CLI

Azure CLI is the command-line tool for managing Azure resources. This is used by the build and deployment scripts to authenticate with Azure and deploy resources.

I chose Azure CLI since it is cross platform allowing me to develop on my Windows machine and yet also work on Travis CI’s Linux machines.

Azure Resource Manager templates

Azure Resource Manager (ARM) templates allow you to define Azure resources using JSON.

Using this means I could define all my infrastructure as code and store in source control, plus Azure CLI integrates nicely with it.

Travis CI

Travis CI is a Continuous Integration tool for GitHub, which I use to build and deploy my GitHub projects.

I chose Travis CI after I read this GitHub blog post. This post showed that the majority of projects on GitHub that use CI, utilise Travis CI. I couldn’t argue with that.

Helm

Helm is a package manager for Kubernetes which I am using to:

  • Provide a templating language for Kubernetes resources. This allows me to easily change the tag of a container image during deployment and similarly, pass in secret values.
  • Define dependencies of the bot such NGINX and Redis. These are available as Helm charts that have already been configured with best practices in mind; which means I don’t have to have in depth knowledge about them. These dependencies get automatically deployed along side my bot.

kubectl

kubectl is the command-line tool for deploying and managing applications on Kubernetes. This is a dependency for Helm.

Defining the Azure resources

The following ARM template defines the individual Azure resources which are used to host and by the bot; these are:

  • Azure Container Service (AKS) — A managed Kubernetes cluster.
  • Application Insights — Logging and analytics for the bot.
  • Bot Channels Registration – a registration to allow communication with the bot through channels such as Facebook messenger.
  • LUIS — Language understanding service which is used by the bot to understand the intent of a user’s message.
  • Storage Account — A state store for the bot.
